## 实测更正（2026-08-30 追加）

本节为 2026-08-30 运行实测基准后对正文的更正与补充，优先级高于正文中的估算值。

**1. 栅格规模（正文 0.1 节需更正）**
当前驱动栅格为 **1560 × 4082 = 6,367,920 像元**（正文记录的 3507 列是修复 `fix_grid_consistency.py` 之前的旧值）。相应地，A2 的内存测算应修正为 `4 变量 × 365 天 × 6,367,920 像元 × 4 B ≈ 37.2 GB`。

**2. 无效像元占比（新增）**
研究区有效像元 **3,717,422（58.4%）**，即 **41.6% 的算力被浪费在 nodata 上**。正文 A 类未单列此项，它是独立于语义修正的一次免费 1.71× 提速。

**3. 输出压缩格式的兼容性红线（重要，本条已修订两次，以本节为准）**

压缩格式**不能只看读写性能，必须落在前端 `webgis_frontend/js/geotiff.js` 支持的集合内**。该库实际注册的解码器为：`1 无压缩 / 5 LZW / 8 Deflate / 7 JPEG / 32773 PackBits / 34887 LERC / 50001 ZSTD(带预测器)`。

实测（1560×4082 float32，研究区外为 NaN，用 node 直接跑前端库验证）：

| 方案 | TIFF tag 259 | 写入 | 文件 | 前端可读 |
|---|---|---|---|---|
| 无压缩 | 1 | 80 ms | 25.5 MB | 是 |
| **LZW** | 5 | 441 ms | **19.8 MB** | **是（当前采用）** |
| Deflate + predictor=3 | 8 | 713 ms | 13.4 MB | 是（数值一致） |
| ZSTD + predictor=3 | **50000** | 481 ms | 13.3 MB | **否** |

两个坑：
- **GDAL 的 zstd 一律写 tag 50000**，与 `predictor` 取 1/2/3 无关；而该 geotiff.js 只注册了 50001。于是前端报 `Unknown compression method identifier: 50000`。2026-08-30 曾误改为 zstd 并导致线上报错，已回退。
- **早期"LZW 会膨胀到 31.1 MB"是测量假象**——那次用随机数填充测试，LZW 对随机噪声无效。真实径流场（研究区外大片 NaN）LZW 能压到 19.8 MB。

回归测试见 `tests/test_output_frontend_readable.py`，它会直读 tag 259 并用前端库实际解码，防止再次踩坑。

**4. 驱动数据存在两代混存（新增，数据侧问题）**

| 代 | 日期范围 | 文件数 | nodata 编码 | 有效像元 |
|---|---|---|---|---|
| 旧 | 2024-01-01 ~ 2024-04-13 | 104 | 声明为 -3.4e38 哨兵 | 3,125,430 |
| 新 | 2024-04-14 ~ 2024-12-30 | 261 | 未声明，无效值为 NaN | 3,717,422 |

切换点为 **2024-04-14**，且旧一代的有效范围是新一代的**严格子集**（新一代多出 591,992 像元）。后果：任何只按"第一天"确定有效掩膜的实现，在跨 04-14 的模拟中要么丢掉 59 万像元，要么对它们做无意义填充。本轮实施改为**跨日期采样取并集** + 前向填充并上报填充计数。

另注：驱动气温单位为**摄氏度**（实测 -34 ~ 27 ℃），非开尔文。

**5. 推理引擎层手段实测为负收益（新增，避坑）**

| 手段 | 实测 | 结论 |
|---|---|---|
| bfloat16 | 0.07×（慢 14 倍） | 本机无 AMX/VNNI，勿用 |
| `jit.freeze` + `optimize_for_inference` | 0.77× | LSTM 已走 oneDNN 内核，JIT 反而拖慢 |
| `torch.compile`(inductor) | 0.93× | 无收益 |

真正的提速来源是**语义修正 + 掩膜**，不是推理引擎层技巧。

**6. 端到端实测提速倍数（2026-08-30 全链路实测，含读盘/推理/写盘）**

| 口径 | 单日 | 相对旧实现 |
|---|---|---|
| 旧实现（全域 637 万像元） | 159 s | 1× |
| 旧语义 + 只算有效像元 | 102 s | 1.6× |
| 新引擎（修正语义 + 有效像元 + batch 16384） | 21.1 s | **7.5×** |
| 新引擎 + 流域掩膜（79,386 像元，不预热） | 0.6 s | **265×** |

分解：语义修正贡献 4.4×，剔除 nodata 贡献 1.71×，相乘与 7.5× 吻合。
流域 + 180 天预热为 109 s，其中预热占 98%（模拟段仅约 1.8 s），预热状态可缓存复用。

> 注意：本节数值为**端到端实测**，取代正文第 3、5 节中基于计算量的量级估算。
> 微基准只能确定单位成本（约 5.7 µs/像元·步），不能确定基线——基线必须实测。

### 0.2 关键假设（请在采纳方案前确认）

## 1. 结论速览

**最严重的问题不是慢，是"在线服务的径流结果在数学上不成立"。**

模块里存在 **三套互不兼容的 LSTM 序列语义**：

| 环节 | 张量形状 | LSTM 沿什么展开 | 含义 |
|---|---|---|---|
| 训练 `train.py` | `(n_months, max_days, 4)` | **天**（约 28–31 步） | 一个流域一个月的日驱动 → 月径流总量 |
| 离线推理 `predict.py` | `(1, 365, 4)` | **天**（365 步） | 单个像元一整年 → 365 个日值 |
| 在线服务 `simulate.py` | `(1, B, 4)`，B=1024~16384 | **像元** | 一批**空间上相邻的像元**被当成一条时间序列 |

在线服务把"**像元**"当成了"**时间步**"。直接后果：

- 每个像元的预测值依赖**同一批次里排在它前面的所有像元**（行优先展开，甚至跨行），即依赖空间上无关的邻域；
- 预测结果随 `batch_size` 变化、随像元排列顺序变化，**不可复现**；
- **跨日期没有任何状态传递**，模型看不到前期降水与积雪累积 —— 径流模拟最核心的"记忆"被完全丢弃，LSTM 退化为被污染的前馈网络。

设计文档 `03_灾害过程模拟模块技术思路.md` 第 3.1 节写的是"将研究区每个像元视为独立样本"，而实现恰好相反 —— 像元不但不独立，还被强行串成了序列。这是实现与设计的背离，不是设计意图。

## 2. 问题清单

严重程度定义：**致命** = 结果不可用或必然失败；**高** = 显著影响正确性/可用性；**中** = 影响效率或可维护性；**低** = 优化项。

### A. 计算性能

| ID | 问题 | 严重度 | 影响范围 | 证据 |
|---|---|---|---|---|
| A1 | `predict.py` 逐像元 Python 双循环，每个像元一次 `torch` 前向 | **致命** | 离线批量推理 | `predict.py:96-103`，547 万像元 × 一次 kernel launch |
| A2 | `predict.py` 把全年 4 变量一次性 `np.stack` 进内存 | **致命** | 离线批量推理 | `predict.py:91`，约 **31.9 GB**（见下方测算），必然 OOM |
| A3 | 在线服务把像元当时间步，LSTM 串行展开 1024–16384 步 | **致命** | 在线径流模拟 | `simulate.py:317-333` |
| A4 | 全高原 547 万像元**全部**计算，流域裁剪在计算之后 | **高** | 在线径流模拟 | `simulate.py:317` 计算 vs `392-418` 后置裁剪 |
| A5 | 阈值栅格在**日循环内**反复打开并可能反复重采样 | 中 | 洪水淹没分析 | `simulate.py:562-580`（循环内 `rasterio.open(threshold_path)`） |
| A6 | 融雪模块：年最大图**逐日**重复读、GeoJSON **逐日**重复解析 | 中 | 融雪洪水识别 | `snowmelt_flood.py:244` + `136`；`260` + `338-339` |
| A7 | 整个模拟在 Flask 请求线程内同步执行，无任务队列 | **高** | 全模块 | `simulate.py:127`、`snowmelt_flood.py:196` |

**A2 内存测算**：`4 变量 × 365 天 × 5,470,920 像元 × 4 B = 31.95 GB`。现状数据（1560×3507）下该脚本在常规工作站上**必然**内存溢出，不是"慢"而是"跑不完"。

**A3 耗时测算**：像元数 547 万，GPU 批 4096 → 每日 1336 批，每批串行展开 4096 个时间步（batch=1，GPU 利用率极低）；CPU 批 1024 → 每日 5342 批。粗估 **分钟级到十分钟级 / 天**，一个月的模拟是**小时级**。

**A4 浪费测算**：叶尔羌河流域约 5–10 万 km²，驱动栅格全域约 459 万 km²，占比约 1%–2%。即 **98% 以上的算力算在了用户根本不看的区域上**，而且这些无效计算还会因为 A3 的串行污染把流域内的结果一起带偏。

| ID | 问题 | 严重度 | 影响范围 | 证据 |
|---|---|---|---|---|

| B8 | 用**参考文件**的 nodata 去掩膜**所有变量**，且未用 `masked=True` | 中 | 径流模拟 | `simulate.py:238`、`286-307` |
| B9 | 无验证集、无早停、无精度指标；文档要求 NSE ≥ 0.85 但代码中**没有任何评估指标** | **高** | 科研可信度 | `train.py`（仅 fixed 55 epoch + MSELoss） |
| B10 | 径流输出量纲与 `grid_threshold_*p.tif` 量纲未做任何一致性校验 | 中 | 淹没判定 | `simulate.py:585` |
| B11 | 无 warm-up 期：模拟从 `start_date` 冷启动，前期径流必然偏低 | **高** | 径流模拟 | `simulate.py:274` 逐日独立 |

**B7 展开**：年最大值 `yearly_max_data` 就是当年逐像元的最大值，所以 `daily >= yearly_max` 对每个像元而言一年只在其峰值日成立。但 `has_flood` 是全域 `np.sum(...) > 0` —— 只要**任何一个像元**当天到达自己的年峰值就判为洪水日，于是 `flood_probability = flood_days / valid_days` 会趋近 1.0，指标完全失去区分度。

**B6 展开**：`flipped_vals = max_val - (arr - min_val)` 是逐时相的空间反转。它把"当日最大值 ↔ 当日最小值"对调，绝对值变成依赖当日极差的任意量。这一步之后，径流值既不能与阈值场比较，也不能做时间序列分析。

## 3. 优化方案

### A 类 · 计算性能

**A1 / A2 — 离线推理向量化 + 流式聚合（难度：低；收益：极高）**
- 方向：取消逐像元 Python 循环，改为沿**像元维**批量：`X (P, T, V)`，一次前向处理数万像元；年最大图改为 `np.fmax` 流式归约，永不把全年 stack 进内存。
- 预期收益：A1 提速 **100–1000×**；A2 内存从 31.9 GB 降至 **< 1 GB**（按块处理）。
- 关键思路：
  ```
  # 年最大：流式，不 stack
  mx = np.full((H, W), -np.inf, 'float32')
  for f in year_files:
      with rasterio.open(f) as src:
          mx = np.fmax(mx, src.read(1, masked=True).filled(-np.inf))

  # 推理：像元是 batch，天是序列
  X = cube[:, mask].transpose(1, 0, 2)        # (P, T, V)
  for ch in chunks(P, 50_000):
      out[ch] = model(X[ch].to(dev))          # (ch, T)
  ```

**A3 / A4 — 在线语义修正 + 流域掩膜前置（难度：中；收益：极高）**
- 方向：① 修 batch 语义（见 B1）；② 先由流域几何算 bbox，用 `rasterio` **窗口读**只取流域外接矩形，再用 `geometry_mask` 得到有效像元索引，只对这些像元推理。
- 预期收益：语义修正后 LSTM 沿"天"展开（约 30 步）而非 4096 步，单批串行长度降 2 个数量级；叠加掩膜前置后**综合提速 20–50×**。叶尔羌单日推理预计进入**秒级**。

**A5 — 阈值栅格提到日循环外（难度：低；收益：中）**
- 方向：循环外读一次阈值并重采样好；若与径流同 grid（实测一致，1560×3507）直接跳过重采样；确需重采样时用 `rasterio.warp.reproject` 而非 `scipy.ndimage.zoom`（后者忽略半像元配准，会引入系统性偏移）。
- 预期收益：365 天场景省下 365 次大栅格 IO。

**A6 — 融雪模块缓存年最大图与 GeoJSON（难度：低；收益：中）**
- 方向：按 `year` 缓存年最大数组（已有文件缓存，但**每个日期都重新 `rasterio.open` 一次**）；GeoJSON 复用 `load_json_cached`（与 `simulate.py` 对齐，不要 `json.load` 另起一套）。
- 预期收益：365 天场景省 365 次栅格读 + 365 次大 JSON 解析。

**A7 — 任务异步化（难度：中；收益：高）**
- 方向：`POST` 立即返回 `job_id`，后台线程/队列执行，`GET /jobs/{id}` 轮询进度（已处理天数/总天数）与日志；支持取消。
- 预期收益：消除 HTTP 超时与"页面卡死"，为长时间模拟提供进度反馈。

### B 类 · 数值与算法

**B1 — 修正序列语义（难度：中；收益：致命级，最高优先级）**
- 方向：LSTM 必须沿**时间**展开，像元只做 batch。
  ```
  # 错误（现状）：(1, B_pixels, 4) —— 像元被当成时间步
  # 正确：       (B_pixels, T_days, 4)
  X = cube[:, mask].transpose(1, 0, 2)       # (P, T, V)
  y = model(X)                               # (P, T)
  ```
- 配套：长时段用**滑窗 + 状态传递**，保证跨窗记忆不断。
  ```
  h = c = None
  for w in windows(T, win=30, stride=n_out):
      y, (h, c) = model.lstm(x[:, w], (h, c) if h else None)
      h, c = h.detach(), c.detach()          # 截断 BPTT，防显存增长
  ```
- 验收：加一条**语义回归测试** —— `batch_size` 从 1024 改到 8192，输出 RMSE 应 < 1e-6。当前代码这条测试必挂。

**B2 — 统一训练/推理的空间支撑度（难度：高；收益：致命级）**
- 方向（三条路径，建议先走 A 再走 B）：
  - **路径 A（保守，1–2 天）**：维持"逐像元分布式"，则训练也必须改成逐像元 —— 需要**逐像元径流标签**（可用水文模型或面积-径流深分配生成）。
  - **路径 B（推荐，中期）**：改回**流域聚合型** LSTM —— 对流域做空间平均得 `(T, 4)`，输出流域出口月/日径流，语义与现有训练**严格一致**，且能用实测径流算 NSE。栅格化展示用"径流深 × 面积权重"或单位线分配。
  - **路径 C（长期）**：**产流交给 LSTM、汇流交给物理算子** —— LSTM 只输出逐像元径流深，再用 D8 流向 + 运动波/马斯京根做汇流路由。
- 预期收益：从"结果不可用"变为"可验证、可发表"。

**B3 — 输入标准化（难度：低；收益：高）**
- 方向：按变量（或按流域，参考 NeuralHydrology 的 per-basin 标准化）做 z-score，**均值和方差随模型一起持久化**（见 D5），推理时加载同一套参数。
- 预期收益：消除量级失衡导致的训练被气温主导；通常 NSE 提升明显。

**B4 — 处理 padding 污染（难度：低；收益：中）**
- 方向：改用 `pack_padded_sequence` / attention mask，或固定 `T=31` + 显式 mask 并把填充日损失置零；至少不要填"全局均值"这种会被模型当成真实气象的值。

**B5 — 引入物理约束（难度：中；收益：高）**
- 方向：① 输出层 ReLU 换成 `softplus` 或保留 ReLU 但加**水量平衡正则**（长期降水 ≈ 径流 + 蒸散 + 储量变化）；② 引入汇流（见 A 类路径 C）；③ 加入前期影响雨量/度日因子等显式特征，降低对 LSTM 隐式记忆的依赖。

**B6 — 删除数值翻转（难度：低；收益：致命级）**
- 方向：直接删掉 `predict.py:111-116` 的翻转；若当初是为了对齐"某种显示方向"，应改成对**阈值场**做同样的约定，而不是篡改模拟结果。同时重算/重新核对 `grid_threshold_*p.tif` 的来源量纲（B10）。

**B7 — 修正融雪洪水判据（难度：低；收益：高）**
- 方向：把"≥ 年最大值"改为有区分度的判据，例如：
  - 当日融雪量 ≥ 该像元年最大值的 `α` 倍（如 0.8），或
  - ≥ 年融雪序列的 `P95/P99` 分位，或
  - 引入**持续期/总量**条件（连续 N 日超阈）。
- 同时把 `has_flood` 的判定从"全域任一像元"改为"**流域内超阈像元占比 ≥ 阈值或绝对面积 ≥ 阈值**"，否则洪水概率恒为 1。

**B8 — 逐文件 nodata 处理（难度：低；收益：中）**
- 方向：每个变量各自读 `src.nodata`（含 scale/offset），用 `src.read(1, masked=True)` 拿掩膜数组，再对**任意变量缺失**的像元统一置无效。

**B9 — 建立精度评估闭环（难度：中；收益：高）**
- 方向：划分 train/val/test（按水文年而非随机，且留出独立流域做空间泛化检验）；加入早停；实现 NSE、KGE、PBIAS、FHV/FLV/FMS（洪水分位误差）与历史灾情点 ROC。文档已要求 NSE ≥ 0.85，应把指标落进 CI。

**B11 — 增加 warm-up 期（难度：低；收益：高）**
- 方向：请求 `[start, end]` 时自动向前多读 `warmup`（建议 ≥ 365 天，融雪流域更长）驱动，预热后再截取输出段。

## 4. 值得参考的开源项目

以下 5 个均已核实仓库真实存在且近期有更新（2026-08 查询）。

### 1. NeuralHydrology — https://github.com/neuralhydrology/neuralhydrology
（572★，Python，最近更新 2026-08-09）

最值得优先读的项目，**它直接对症 B1、B3、B9**。

- **序列语义的"教科书约定"**：`BaseDataset` 中 `(batch=basin, seq=time, feature)` 的张量组织、`seq_length` / `predict_last_n` / `warmup` 三个显式概念 —— 本项目最缺的就是这三个参数，B1、B11 照抄即可解决。
- **per-basin 标准化**：每个流域单独算均值/方差，正好解决 B3 的气温/降水量级失衡。
- **水文专用损失与指标**：内置 NSE 损失（NSELoss）、KGE、FHV/FLV/FMS 洪水分位误差 —— 直接满足文档"NSE ≥ 0.85"的验收需求（B9）。
- **工程架构**：YAML 配置驱动，每次实验自动落盘配置 + 权重 + 评估结果，可复现（对应 D5、D8）。
- 迁移建议：不必整体替换，把 `seq_length` / `warmup` / per-basin 归一化 / NSE 评估这四件事搬进来即可。

### 2. LISFLOOD OS — https://github.com/ec-jrc/lisflood-code
（167★，Python，最近更新 2026-08-18）

栅格分布式水文的成熟工程范式，**对症 B5 的"无汇流"和阈值法简化**。

- `src/lisflood/hydrological_modules/kinematic_wave_parallel.py`：**运动波汇流的并行实现**，可直接替换当前"径流 ≥ 阈值即淹没"的零维判定，给出洪峰传播与时空滞后 —— 正是设计文档第 7 节列为"已知边界"的那一项。
- `routing.py` / `surface_routing.py`：D8 流向 + 汇流滞后；
- `snow.py` / `frost.py`：度日因子积雪与冻土模块，契合寒区场景；
- `waterbalance.py`：水量平衡核算，可用来给 LSTM 输出加物理诊断（B5）；
- 全栅格 + NetCDF 时序输出 + PCRaster 风格算子，与本项目"逐日栅格"的输出形态高度一致。

### 3. HydroMT — https://github.com/Deltares/hydromt
（119★，Python，最近更新 2026-08-19）

**专治 C 类和 D3**：把"ERA5/GLDAS 栅格 + 流域矢量 → 模型输入"这段数据准备彻底工程化。

- `DataCatalog`：YAML 声明式数据源，消灭 `F:\output2` 式硬编码；
- 栅格/矢量懒加载、`clip` / `reproject` 与流域聚一体化 API —— 直接解决 C1（全图读）与 A4（裁剪滞后）；
- 声明式、可复现的模型构建流程；
- 内置 Wflow / SFINCS / Delft3D 插件，是未来耦合水动力的现成桥梁。

### 4. Wflow.jl — https://github.com/Deltares/Wflow.jl
（162★，Julia，最近更新 2026-08-27）

**专治 A2 的内存架构问题**，借鉴设计思想即可，不必换语言。

- **分块流式**：按子流域/时间分块计算、NetCDF 分块写出，从不把全年数据 stack 进内存 —— A2 的 31.9 GB 问题的正面答案；
- **"静态输入 + 动态输入 + 状态变量"三层划分**：本项目现在只有动态输入、没有任何状态变量，这正是 B11（无 warm-up）和跨批次无记忆的根因；
- 运动波/马斯京根汇流 + 雪/土壤/地下水多层结构，是引入物理过程的参考实现。

### 5. hydroDL — https://github.com/mhpi/hydroDL
（242★，Python，最近更新 2026-02-04）

**专治 B2 的"只有一个流域、只有月标签"**。

- 面向**多流域、多样本**的 LSTM 径流训练范式，其 data 模块对 CAMELS 类数据集的 `(basin, time, feature)` 组织与时段划分可直接照搬，把本项目从"叶尔羌单流域"扩展到青藏高原多流域；
- 含 **dPL（可微参数学习）**思路：用 LSTM 输出物理模型参数而非直接输出径流 —— 是"DL 替代物理"路线的升级方向，在保留数据驱动拟合能力的同时拿回可解释性与物理一致性。

> 备选：**SuperflexPy** — https://github.com/dalmo1991/superflexPy（61★，Python，更新至 2026-07）模块化水文建模框架，若你打算把"产流/汇流/雪模块"做成可插拔组件，它的组件抽象值得参考。

## 7. 一句话总结

**先修语义，再谈提速。** 当前在线径流服务把"空间像元"当成"时间步"喂给 LSTM，导致结果依赖批大小与像元排列顺序、跨日期无任何记忆 —— 在这个前提下做任何性能优化，都只是让错误结果出得更快。P0 五项（修语义、停填 0、掩膜前置、修融雪判据、删数值翻转）预估 3–5 天，能让模块从"结果不可用"跳到"可用且快 20–50 倍"，是投入产出比最高的部分。
